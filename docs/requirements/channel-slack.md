## What this is

What wakes a Rundesk agent on Slack, what it can be asked for without saying anything to its brain,
where its answer goes, and how little it shows while it works.
Everything about the platform lives in `src/channels/slack` and nowhere else; adding it needed one
change under `src/rundesk/` — the typed authorization address `R-CH-39` and `R-CAD-25` describe —
and no change to the record vocabulary.

The `SLK` namespace was withdrawn on 2026-08-25 with the previous build's Slack contract and is
reissued here. Nothing in the tree cites the old rows, and they remain in git history only.

## Why it exists

- An agent stands in somebody else's workspace and is silent there until it is named.
- Several separately installed agents can share one thread without waking each other.
- Nothing an agent posts into a shared channel is bookkeeping about the answer rather than the
  answer, so a channel full of people reads a conversation and not a build log.
- Two agents working in one thread can each read what the other answered, so a person can ask one
  what it makes of the other's reply.
- An owner can steer the agent and read what the install knows from Slack itself, privately, and
  without spending a turn on the question.
- One agent's command cannot take another agent's command away from it, in a workspace where both
  are installed.
- An agent can name one person in an answer and can never address a room full of them.
- No Slack user OAuth token, and no scope that reads a channel the bot was not invited to.
- An agent can look through the conversations its own bot is in, on demand, without anybody
  pasting them to it — and cannot look anywhere else.

## Open questions

- Whether Markdown a brain wrote should be translated into Slack's `mrkdwn` dialect. It is not
  today: `**bold**` reaches Slack as the characters typed, and only the reserved `&`, `<` and `>` are
  escaped. A partial translation that touched a fenced code block would be worse than none.
- What a rate limit with no usable `Retry-After` should cost. The status mechanism stops until the
  channel is started again, because there is no interval to invent and Slack says a caller must wait
  for the response's delay before using that method in that workspace again. Whether Slack ever
  answers a 429 on this method without a `Retry-After` is unknown, and only a real workspace answers
  it.
- Whether the agent declaration can be made in an app manifest. Slack's reference publishes no key
  for it, so [the guide](../guides/slack.md) makes it an ordered step in the app's own settings and
  none is invented here. If one is published, the manifest and that step move together.
- What becomes of a direct conversation recorded under the older key, and **the answer is not
  settled and nothing has been done about it**. Before `R-SLK-50` a threaded direct message keyed
  its own conversation, so an install where somebody replied inside a DM holds rows under
  `<workspace>:<channel>:<thread>` that nothing addresses now: their messages, turns and provider
  session are still on disk, still readable through `rundesk messages`, and no longer reached by a
  new message in that direct conversation. Nothing is lost and nothing is wrong; what is missing is
  continuity for those particular exchanges. Merging them means choosing one surviving conversation
  row, repointing `conversation_messages`, `turns` and `delegations.parent_conversation` at it, and
  deciding what happens to two `provider_sessions` rows that cannot both survive one primary key —
  and identifying which `source_id` is a *direct* conversation needs Slack's own id shape, which is
  knowledge `src/rundesk/` deliberately does not hold. So the shape of the fix is an owner decision
  rather than a shipped migration written on the way past, and it is deliberately unmade here.
- Whether a direct answer belongs in a thread at all. The previous build threaded one and took it
  back out, on the grounds that a thread hides a reply behind a click; it is threaded again here
  because one direct conversation now holds every exchange and a thread is what keeps two of them
  readable apart. Which reads better in practice is a thing only somebody using it can say.
- **Settled: a file that arrives is landed, and `files:read` is demanded** (R-SLK-66). The owner
  chose the Discord behaviour over the reinstall-free one: an app that cannot read a file drops
  what people send it. What it costs is one reinstall per app installed before the scope was
  wanted, and the guide names the refusal and the fix.
- Whether a partial attachment failure should settle the whole turn as failed. It does today, so
  nothing ticks a delivery that arrived in part, and the words and the reason are both visible. The
  alternative — reporting it delivered and leaving the failure to the log — puts a completion mark
  over an answer with a piece missing, which is the outcome that was rejected.
- Whether a command typed inside a thread should reach that thread's conversation. Slack's command
  payload carries no `thread_ts`, so it cannot today: `stop`, `new` and `delegations` are about the
  channel's own conversation, which is exactly right in a direct message and is one step too wide in
  a channel where turns run in threads. Nothing here remembers the newest thread a channel answered
  in and uses that, because a stop that silently ended a different thread's turn is worse than one
  that says nothing is running. Whether Slack ever puts the thread in that payload is Slack's to
  answer.
- Whether a mention an agent wrote should be narrowed to the people the channel allows. It is not
  today: any exact `<@U…>` or `<@W…>` token survives, so an agent talked into naming somebody
  notifies that one person. What decided it is the blast radius — one person reads a line meant for
  them, against a room full of people interrupted — and narrowing it to the allow list would also
  stop an agent naming the colleague it was correctly asked to loop in.
- Whether the `commands` scope is really required to declare a slash command in an app manifest.
  Slack publishes the scope as the one that adds shortcuts and slash commands, so the manifest asks
  for it and `WANTED_SCOPES` deliberately does not: a channel whose app never declared a command
  works unchanged for messages, and refusing one over a scope it does not need would break every
  Slack channel installed before the command existed. Only a real workspace paste settles it.
- Whether a bounded thread slice should also be carried for a mention that opens its own thread,
  from the channel above it rather than from the thread. It is not today, and the channel above is
  not something the agent was invited into a conversation about.
- What a thread past the read ceiling should carry. `conversations.replies` pages forward, so the
  pre-mention thread is walked to its end and only the newest lines are kept; past 500 messages the
  walk stops, says so in the agent's log, and carries lines that are genuinely earlier in the thread
  rather than directly above the question. Whether that is better than carrying nothing there is not
  settled, and only a real workspace says how often it happens.
- Whether an app mismatch should ever cost more than a line. It costs exactly that today: the
  channel is greeted, reports ready and goes on running, and the log says which two tokens to
  reissue. Acting on it — refusing readiness, or ending the adapter the way a revoked credential
  does — would take an agent off Slack on the strength of a comparison **no live workspace has yet
  answered**, and a wrong verdict there costs more than the silence it describes. What Slack really
  puts in `hello.connection_info` for an app installed by hand, or across an Enterprise Grid, is
  what settles it, and only a real workspace says.
